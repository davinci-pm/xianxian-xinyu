# 女娲「蒸馏人」工作室：产品与技术方案 V0.2

> 状态：P0 内测纵切已实现，待线上验收
> 日期：2026-08-29
> 范围：产品定义、技术架构、数据契约、质量门禁和实施路线

本次已实现 `/studio`、`/studio/new`、`/me`，以及项目创建、文本资料写入、校准、确定性蒸馏、质量评分、证据主张、不可变人物版本、会话版本锁定和按用户隔离。对象存储、后台异步任务、人工证据审核、导入导出、删除链路与受控分享仍按本文后续阶段推进。

本版已冻结的产品方向：**不建设人物广场；数字人生成后进入创建者的个人主页，供本人管理和使用。**

## 1. 结论先行

建议把新能力拆成两个相连的页面域：

1. **女娲工坊**：用户上传资料，生成、审核、预览、迭代和导出人物资产。
2. **我的数字人**：数字人生成后展示在用户个人主页，可直接对话、继续补充资料、切换版本和导出。

产品不提供全站人物广场、榜单、信息流或公共搜索。数字人默认私有；后续可以提供“仅链接可见”和“个人公开主页可见”，但公开可见仍属于对外发布，需要单独通过权利和隐私门禁。

首个可用版本只做“女娲工坊 + 登录后个人主页里的私有数字人”。当前项目还需要先补齐：

- 真正的人物版本表，以及会话对人物版本的锁定；
- 独立创作者账号和资源所有权；
- 面向原始资料的私有对象存储与异步任务；
- 授权、隐私、可见性和完整删除链路。

“蒸馏人”的技术本质也需要说清楚：

- 它不是训练出一个新的基础模型，也不是复制意识；
- 它是把资料转换成一份**可追溯、可版本化、可评测的人物运行资产**；
- 运行资产由人物认知框架、表达规则、事实与时间线、证据索引、诚实边界、对话策略和专属 RAG 知识库组成；
- 产品可以说“和基于这些资料构建的数字人物对话”，不能承诺“完全复制本人”或“AI 已经变成本人”。

核心成功标准不是“口吻像”，而是：

> 面对资料没有直接回答过的新问题，它能否基于有证据的价值排序和思考方式，产生有用、独特、诚实且可解释的回答。

## 2. 产品目标与非目标

### 2.1 产品目标

- 让普通用户不写提示词，也能把聊天记录、文章、访谈、时间线等资料整理成人物资产。
- 让创建者看到每个事实、特征和推断来自哪里，并能逐项修正。
- 让人物资产可以下载备份、再次导入、创建新版本。
- 让生成后的人物直接进入创建者个人主页，成为可持续补充和使用的私人资产。
- 让“套路识别、沟通训练、思想学习、亲友纪念、自我复盘”等场景产生实际内容价值。

### 2.2 非目标

- 不复制或上传模型权重，不在第一阶段做模型微调。
- 不宣称恢复逝者意识、读取真人内心或代表真人当前观点。
- 不允许用产品冒充真人联系第三方、诈骗、骚扰或制造本人背书。
- 不在第一阶段做声音克隆、视频分身、实时电话或社交账号代发。
- 不把用户上传的私人聊天默认放进公开人物包。
- 不保证人物包可以直接运行在任意第三方 AI 产品；跨平台适配应通过后续导出适配器实现。

## 3. 功能命名与信息架构

建议的产品命名：

- 一级入口：**女娲工坊**
- 主行动按钮：**创建人物**
- 创作项目：**人物草稿**
- 可下载资产：**人物包**
- 个人主页模块：**我的数字人**

“蒸馏人”适合作为功能概念和传播词，但界面主文案应优先使用“创建数字人物”“从资料生成人物”，降低用户对“复制真人”的误解。

建议新增页面：

| 页面 | 路由 | 作用 |

## 4. 人物类型与权利门禁

创建第一步必须先选人物类型。不同类型不能共用一套发布规则。

| 类型 | 示例 | 私有创建 | 个人公开主页展示 |
| --- | --- | --- | --- |
| 自己 | 用自己的日记、文章和聊天蒸馏自己 | 允许 | 本人确认后可申请 |
| 经授权的在世私人个人 | 同事、朋友、伴侣、导师 | 有合法资料来源并完成声明后允许 | 需要可验证的本人授权；默认禁止 |
| 在世公众人物 | 创业者、作家、内容创作者 | 仅限合法公开资料 | 需要来源、肖像/姓名和人格权审核，明确非本人 |
| 已故人物 | 历史人物、已故亲友 | 视资料权利而定 | 需要版权、家属/遗产权益和敏感性审核 |
| 合成人物 | “常见渣男套路”“高压老板” | 允许 | 必须去可识别化，标记为合成教学角色 |
| 虚构角色 | 用户原创角色 | 允许 | 创建者声明原创或拥有授权后可申请 |

### 4.1 聊天记录的特殊规则

一份聊天记录通常同时包含上传者和第三方的内容。上传者拥有文件，不等于拥有公开传播和人格复制对方的权利。

因此系统必须：

- 要求用户指定“要蒸馏的说话人”并完成说话人映射；
- 默认删除手机号、地址、证件、账号、密钥、健康和财务等敏感信息；
- 默认只生成私有人物；
- 未取得其他参与者授权时，原始聊天不得进入公开导出包；
- 公开的合成人物只能保留聚合后的模式，不保留可反查具体个人的细节、原句和事件组合；
- 支持权利人投诉、验证、下线、删除和版本撤回。

“渣男套路”建议产品化为**关系识别训练角色**：

- 对话模式：模拟常见操控、回避、贬低、推拉等沟通模式；
- 揭示模式：用户点击“看套路”，展示本轮使用了什么模式、危险信号和依据；
- 复盘模式：给出更健康的边界回应，但不替用户诊断具体真人；
- 禁止根据某个可识别对象生成诽谤标签，也禁止教用户如何更有效地操控他人。

### 4.2 用户需要上传或填写什么

系统不应该要求用户先整理成专业人物档案。用户只需要完成四类**必需输入**，其他资料按质量需要逐步补充。

#### 必需输入

| 类别 | 用户提供什么 | 系统为什么需要 |
| --- | --- | --- |
| 人物基础卡 | 昵称或名称、人物类型、语言、与创建者的关系、希望数字人做什么 | 确定身份边界、用途和生成目标；不强制填写真实姓名 |
| 核心语料 | 聊天记录、文章、日记、邮件或访谈转录中至少一种 | 学习这个人实际怎样说、怎样解释和怎样做判断 |
| 来源与说话人 | 哪些话是谁说的、资料大致时间、是否完整、能否使用 | 防止把创建者或第三方的话误蒸馏给目标人物 |
| 权利与隐私声明 | 资料来源、是否获得本人或参与者同意、允许的可见范围 | 决定只能私有使用，还是可以通过链接或个人公开主页展示 |

#### 推荐补充资料

| 资料 | 能增强什么 |
| --- | --- |
| 长对话与语音转写 | 临场思考、互动节奏、追问和犹豫方式 |
| 长文章、日记、博客、邮件 | 稳定观点、价值排序、叙事方式和表达 DNA |
| 关键人生时间线 | 观点形成原因、阶段变化和资料截止时间 |
| 真实决策案例 | 面临什么选择、当时怎么判断、最后怎么做、后来如何复盘 |
| “他绝不会做什么” | 价值底线、反模式和安全边界 |
| 典型矛盾或观点变化 | 避免把复杂的人压平成几个标签 |
| 代表性回答与错误示例 | 哪种回答“很像”，哪种回答“绝对不像” |
| 自述校准问卷 | 在语料不足时补充价值观、冲突处理和沟通习惯 |
| 头像或原创视觉资料 | 只用于页面展示，不参与思想蒸馏；需要独立权利确认 |

不需要、也不应该上传：身份证、银行卡、密码、密钥、通讯录、精确住址、无关第三方隐私、未经许可的私密影像。

#### 建议的数据充足度分档

以下是首版产品的操作性建议，需要用真实样本验证后再调整；它不是“字符越多就一定越像”的科学结论。

| 档位 | 建议资料量与覆盖 | 可以生成什么 |
| --- | --- | --- |
| 试生成 | 5,000～20,000 个有效中文字符，至少覆盖 3 个不同场景 | 可预览的初版人物；显著标记资料不足，不允许对外展示 |
| 可使用 | 30,000～100,000 个有效字符，至少 5 个场景、5 个真实判断案例，并有基本时间信息 | 可在个人私有主页稳定使用的人物 V1 |
| 高保真 | 100,000 个以上有效字符，多种资料类型、明确时间线、观点变化、反例和留出测试集 | 可申请仅链接或个人公开主页展示的精品版本 |

系统不应只显示字数，而应给出六项“资料健康度”：

1. 表达样本；
2. 思考与解释样本；
3. 决策案例；
4. 价值底线；
5. 时间跨度；
6. 冲突和反例。

缺少某项时，界面直接告诉用户“再补什么最有价值”，而不是笼统要求继续上传。

#### 不同目标的资料重点

- **蒸馏自己**：日记、长期文章、真实决策复盘和本人校准问卷最有价值。
- **经授权的熟人**：目标人物自己的长对话和语音转写优先；创建者对他的评价只能作为二手资料。
- **历史或公众人物**：一手著作、演讲、访谈、决策记录和时间线优先；二手评价必须单独标识。
- **关系套路训练角色**：上传内容先去标识化，再为片段标注场景、使用的沟通模式、对方反应和结果；系统蒸馏共性，不复制某个人。

#### 上传向导

建议把用户操作控制在五步：

```text
1. 创建人物基础卡
2. 上传资料或导入聊天包
3. 映射说话人、时间和资料来源
4. 查看隐私扫描与资料健康度，补答校准问题
5. 确认开始蒸馏
```

校准问卷不做成长问卷，首轮约 8～12 题，并根据已有资料动态跳过。问题示例：

- 他遇到冲突时通常先讲事实、关系还是原则？
- 有哪三件事他大概率不会妥协？
- 他做过哪次典型选择，最能说明他的判断方式？
- 哪种听起来聪明的回答，其实最不像他？
- 哪些主题资料不足，数字人应该明确说“不知道”？

## 5. 三层“记忆”模型

人物资产与聊天记忆必须彻底分开。

| 层 | 内容 | 所有者 | 是否跟随人物包导出 |
| --- | --- | --- | --- |
| 人物认知资产 | 思想模型、价值排序、表达 DNA、事实、时间线、证据、边界 | 人物创建者/版本 | 是 |
| 关系记忆 | 某个用户与某个人物之间已确认的偏好、未解决问题和共同上下文 | 当前用户 | 否 |
| 会话历史 | 单次或多次对话消息、引用和生成记录 | 当前用户 | 否，除非用户主动导出自己的对话 |

现有 `memories` 表和人物级隔离继续服务“关系记忆”。它不能被混入人物版本，也不能在人物被分享、派生或公开后转移给其他用户。

## 6. 用户流程

### 6.1 创建流程

```text
选择人物类型与用途
  → 声明资料权利和期望可见范围
  → 上传资料包
  → 格式解析、说话人映射、查毒与解压安全检查
  → 去重、脱敏、切分、语言与时间识别
  → 提取事实、时间线、观点、行为模式和原始证据
  → 识别冲突、观点演化和信息缺口
  → 蒸馏心智模型、决策启发式、价值张力和表达 DNA
  → 生成人物草稿、专属 RAG 和评测集
  → 自动质量评测
  → 创建者逐项审核与修正
  → 私有预览对话
  → 冻结人物版本
  → 写入个人主页 / 导出备份 / 后续可选受控分享
```

### 6.2 证据审核界面

每条蒸馏结论必须以卡片展示：

- 结论：例如“遇到不确定性时倾向先做小规模试验”；
- 类型：事实 / 稳定观点 / 心智模型 / 风格 / 推断 / 冲突；
- 置信度；
- 支持证据，精确到源文件、说话人、时间和段落；
- 反证或矛盾证据；
- 适用范围与局限；
- 操作：接受、修改、降级为推断、排除。

未经创建者确认的低置信结论不得进入发布版本。

### 6.3 对话预览

预览不是普通聊天页的复制，应包含：

- 回答正文；
- “依据”抽屉：本轮检索到的来源和使用的人物原则；
- “这是原话 / 资料概括 / 框架推断”标识；
- 反馈：像、不像、空泛、事实错、越界、有启发；
- 一键回到对应蒸馏卡片修正；
- 清空预览历史，不影响正式人物版本。

## 7. 女娲方法论如何接入

已核验的上游仓库是 [`alchaincyf/nuwa-skill`](https://github.com/alchaincyf/nuwa-skill)，许可证为 MIT。调研时主分支固定提交为 [`fe0374687037c4cc51a65c1e0c145afe2981dc69`](https://github.com/alchaincyf/nuwa-skill/commit/fe0374687037c4cc51a65c1e0c145afe2981dc69)。

可吸收的方法：

- 从著作、对话、表达、外部评价、决策记录、时间线六个维度组织资料；
- 心智模型通过“跨域复现、有生成力、有排他性”三重验证；
- 提取 3～7 个心智模型和 5～10 条决策启发式；
- 量化句长、疑问句、类比、第一人称、确定性和转折等表达 DNA；
- 不抹平时间性矛盾、领域性矛盾和价值张力；
- 对未知问题明确标记框架推断；
- 使用独立的答题角色和评分角色做保真度评测。

不建议直接照搬的部分：

- 上游是给通用 Agent 使用的 `SKILL.md`，会指挥搜索、多 Agent、文件写入和生成新 Skill，不是 Web 后端库；
- 上游模板强调第一人称持续扮演，本产品仍应由平台的身份、安全、引用和危机策略拥有最高优先级；
- 用户上传内容可能包含提示注入文本，不能作为可执行指令加载；
- 上游的质量分可以作为参考，但不能替代本产品的权利、隐私、安全和内容价值门禁。

后续实施时建议：

1. 不使用 `npx skills add` 作为生产集成方式；
2. 以固定 commit 将允许使用的方法论文档离线登记；
3. 保留 MIT LICENSE、版权声明和修改说明；
4. 将其转换成平台自有的结构化蒸馏步骤和评测规则；
5. 上游升级只做人工评审，不自动覆盖生产版本。

## 8. 人物包格式

建议定义平台自己的数据型开放格式：`Sage Persona Package v1`，文件扩展名为 `.persona.zip`。

它必须是**纯数据包**，不得携带或执行脚本、插件、工具权限、网络请求和安装指令。

### 8.1 包结构

```text
persona-package/
├── package.yaml                 # 格式版本、人物版本、创建信息、完整性哈希
├── profile.yaml                 # 身份、类型、简介、主题和展示字段
├── cognition.yaml               # 心智模型、启发式、价值排序、张力与局限
├── style.yaml                   # 表达 DNA、语气、禁用表达、对话动作
├── boundaries.yaml              # 身份、安全、事实、专业建议和隐私边界
├── openings.yaml                # 审核过的开场和快捷回复
├── evidence/
│   ├── claims.jsonl             # 事实/观点/推断及其证据引用
│   └── timeline.jsonl           # 时间线与观点演化
├── sources/
│   ├── index.jsonl              # 来源元数据、权利、哈希和定位
│   └── files/                   # 仅所有者完整备份包可选
├── eval/
│   ├── cases.jsonl              # 版本评测题
│   └── report.json              # 质量报告
└── LICENSES/                    # 第三方许可和署名
```

### 8.2 两种导出包

| 导出类型 | 包含内容 | 使用场景 |
| --- | --- | --- |
| 所有者完整备份包 | 人物资产、评测、原始资料或其加密副本 | 用户迁移、备份、继续编辑 |
| 可分享运行包 | 人物资产、证据元数据、获准使用的短节选，不含私人原始聊天 | 个人主页展示、仅链接分享和运行 |

公开发布不能仅靠删除文件名来脱敏。需要对正文、时间、地点、罕见事件组合和引用片段做再识别风险检查。

### 8.3 `package.yaml` 最小字段

```yaml

package_id: pkg_xxx
persona_id: persona_xxx
version: 1.0.0
persona_type: composite
display_name: 关系套路识别训练员
language: zh-CN
source_cutoff: 2026-08-29

  basis: user_attestation
  public_distribution_allowed: false

  claim_count: 86

  files_manifest: checksums.json
```

### 8.4 聊天记录标准化

不同平台的导出文件先通过适配器转换为内部 JSONL：

```json
{"conversation_id":"c1","message_id":"m1","timestamp":"2026-01-01T10:00:00+08:00","speaker_id":"s1","speaker_label":"本人","text":"...","attachments":[]}
```

第一阶段只承诺：

- `.txt`、`.md`、`.csv`、标准 `.jsonl` 和安全 `.zip`；
- 用户手动映射说话人；
- 不支持的第三方导出先给出转换说明，不静默猜测字段；
- PDF、OCR、音频和视频转录作为后续增量能力。

## 9. 内容价值与质量门禁

在个人主页中使用的数字人不能只靠“像”来通过。建议采用以下 100 分内容价值评分：

| 维度 | 分值 | 核心问题 |
| --- | ---: | --- |
| 证据忠实度 | 25 | 事实、观点和引用是否能回到原始资料 |
| 认知与决策价值 | 25 | 是否提炼出了可用于新问题的思考方式，而非语录拼贴 |
| 对话实用性 | 20 | 是否能帮助用户理解、判断、演练或行动 |
| 人物辨识度 | 15 | 去掉姓名后是否仍有稳定而不过度夸张的差异 |
| 边界诚实度 | 15 | 未知、矛盾、推断和资料截止时间是否说清楚 |

发布门槛建议：

- 私有预览：允许低分，但必须展示缺口和风险；
- 不公开链接：总分至少 70，且无阻断项；
- 个人公开主页可见：总分至少 80，且权利、安全、隐私、来源四项门禁全部通过；
- 权利不清、可识别私人信息、严重事实伪造、跨人物资料污染和高风险安全失败属于阻断项，不能用总分抵消。

自动评测至少包括：

- 3 道资料中有明确立场的问题；
- 2 道资料未覆盖的问题，检查是否诚实标记推断；
- 3 道现实应用题，检查认知框架是否有生成价值；
- 去姓名风格盲测；
- 引用定位与原文一致性抽检；
- 提示注入、身份冒充、隐私套取、医疗/投资/违法和依赖诱导测试；
- 人物隔离测试，错误检索其他人物分块必须为 0。

评测回答与评分应使用彼此隔离的运行上下文；公开发布仍需人工复核，不能让生成模型自评自证。

## 10. 当前架构审计

### 10.1 可以直接复用

| 当前能力 | 复用方式 |
| --- | --- |
| `Persona` | 继续作为人物稳定身份和目录记录 |
| `KnowledgeDocument / KnowledgeChunk` | 承载人物版本的来源与 RAG 分块 |
| BM25 + 向量 + RRF | 复用为蒸馏人物的运行时检索 |
| Persona Pack 校验 | 升级为数据库人物版本发布校验 |
| Skill allowlist 与运行时净化 | 复用“不执行外部指令”的安全原则 |
| `Conversation / Message` | 复用正式对话链路 |
| `Memory` | 继续承载用户与人物的关系记忆 |
| SSE 流式输出 | 复用预览和正式聊天 |
| S3 配置 | 扩展为私有源文件和人物包对象存储 |
| 安全与引用 | 纳入每个人物版本的发布测试 |

### 10.2 必须补齐

1. 当前 `Persona.pack_version` 只是字符串，没有真正的 `persona_versions` 实体。
2. 当前 `Conversation` 只绑定 `persona_id`，没有锁定 `persona_version_id`。
3. 当前 `PersonaPack` 从仓库文件和固定注册表读取，不支持用户草稿、版本审核和回滚。
4. 当前邀请码会映射为内测账号，适合测试，不适合创作者身份、找回、权利申诉和公开资产管理。
5. 当前 S3 主要保存 SQLite 快照，还没有用户文件上传、对象级权限、加密和删除能力。
6. 当前 SQLite + S3 快照适合小规模内测，不适合异步蒸馏任务和多实例并发写入。
7. 当前没有任务队列、资料解析器、创作审核后台和举报流程。

### 10.3 架构决策

- 私有原型可以继续使用 SQLite；进入多人创作内测前迁移到托管 PostgreSQL。
- 原始资料与导出包存私有对象存储，数据库只保存元数据、权限、状态和对象键。
- 蒸馏使用异步 Worker，不占用普通 FastAPI 请求和对话流式连接。
- 引入 `PersonaRuntimeRepository` 抽象：现有人物和用户发布人物最终都读取“已发布版本快照”。
- 会话创建时锁定人物版本；人物升级只影响新会话，历史会话仍可追溯。
- 导入资料永远按“不可信数据”处理，不能进入系统提示的指令区，也不能触发工具。

## 12. 服务拆分

建议新增以下领域服务，第一阶段仍可放在同一个后端代码库：

| 服务 | 职责 |
| --- | --- |
| Upload Service | 签名上传、大小/MIME/哈希、查毒、解压保护、对象权限 |
| Import Adapter | 把文本、Markdown、CSV、JSONL 和 ZIP 转为标准片段 |
| Privacy Processor | PII 检测、说话人映射、脱敏建议和删除 |
| Evidence Extractor | 提取事实、观点、时间线、冲突和证据定位 |
| Persona Distiller | 生成认知、风格、边界、开场和运行快照 |
| Evaluation Service | 确定性校验、模型盲测、安全测试和质量报告 |
| Persona Lifecycle Service | 版本冻结、审核、激活、回滚、停用、可见性和导出 |
| Runtime Repository | 为正式聊天提供不可变的已激活人物快照 |

异步任务状态：

`queued → scanning → parsing → redacting → extracting → distilling → evaluating → awaiting_review → ready`

每个阶段必须可幂等重试，并记录输入哈希、提示模板版本、模型版本和成本。失败后只重跑受影响阶段，不能从头重复消耗。

## 14. 安全、隐私与平台治理

### 14.1 上传安全

- 文件扩展名与实际 MIME 双重校验；
- 单文件、总包、文件数和解压后总大小限制；
- 阻断 Zip Slip、符号链接、嵌套压缩包和压缩炸弹；
- 查毒后才能进入解析队列；
- HTML、Markdown 和聊天正文按纯数据处理；
- 不执行宏、脚本、二进制、Skill 工具指令或包内链接；
- 每个租户使用隔离对象键和短时签名 URL。

### 14.2 隐私

- 上传前明确提示资料会被怎样处理；
- 原始资料默认私有，并与公开运行包分离；
- 未经单独、明确同意，不将私人资料用于全局模型训练；
- 支持项目、原始资料、人物版本和关系记忆分别删除；
- 删除需同步对象存储、数据库、检索索引、缓存和待执行任务；
- 原始资料保留期、备份删除周期和申诉留存期必须在上线前冻结并披露。

### 14.3 身份与误导

- 人物详情和首次会话明确说明其为 AI 人物；
- 资料未覆盖的内容标记“框架推断”；
- 在世真人不得声称获得授权，除非平台已核验且展示授权类型；
- 不允许人物要求用户保密、建立排他依赖或冒充本人联系外部；
- 肖像、声音和姓名权独立审核，不能因为文本资料可用就自动通过。

### 14.4 个人主页展示治理

- 默认只在登录后的本人主页展示；
- 仅链接或个人公开主页可见需要机器预检、必要时人工审核和版本冻结；
- 权利人可以申诉，平台能够临时停止外部访问；
- 举报类别：冒充、隐私、版权、诽谤、危险建议、低质/误导；
- 停止外部展示不篡改历史审计，但终止新访客会话；
- 产品不提供全站搜索、榜单、推荐流、公开评论或社区派生；
- 商业分成和付费下载在权利规则稳定前不进入首版。

## 15. 分阶段路线

### Phase A：版本基础

目标：让现有人物先具备真正可追溯的版本。

- 新增 `persona_versions`；
- 会话锁定 `persona_version_id`；
- 把现有文件人物包迁移成已发布版本快照；
- 支持校验、发布、回滚和历史追溯；
- 不新增用户上传入口。

验收：人物发布新版本后，旧会话仍读取旧版本的身份、开场、知识和引用。

### Phase B：私有女娲工坊

目标：一位登录用户可以从安全文本资料创建私有人物。

- 新建项目、文本/Markdown/CSV/JSONL/ZIP 上传；
- 说话人映射、去重、脱敏和证据提取；
- 蒸馏草稿、证据审核、私有预览；
- 生成 `.persona.zip` 所有者备份包；
- 人物只有创建者可见，不提供公开链接。

验收：用一份标准聊天包和一组文章各完成一次端到端创建；任一核心结论可定位到原始片段。

### Phase C：质量与增量版本

目标：人物不只是能聊，而是具有稳定内容价值。

- 独立评测上下文、价值评分和安全门禁；
- 增量上传，只重算受影响的结论和分块；
- 版本差异、创建者纠正、回滚；
- 导出可发布运行包；
- 预览反馈回流蒸馏卡片。

验收：人物对新问题的回答通过来源、价值、辨识度、诚实边界和安全测试。

### Phase D：个人主页展示与受控分享

目标：让用户在不建设广场的前提下，决定数字人如何出现在自己的页面。

- 私有、仅链接、个人公开主页三档可见性；
- 个人主页展示质量、来源、授权和版本摘要；
- 权利人申诉、快速下线、版本透明；
- 合成人物的教学模式和套路揭示。

验收：未通过权利或质量门禁的人物无法对外展示；任一外部可见人物均可查看版本、来源覆盖和边界摘要，且不会出现在全站广场或榜单。

### Phase E：多媒体与跨平台

- PDF/OCR、音视频转录；
- 共同维护、协作者和授权工作流；
- Agent Skill / Character Card 等只读导出适配器；
- 声音、形象和实时分身单独立项并重新做法律与安全评审。

## 16. 建议的第一条纵向切片

不要先拿真实私人对象做公开测试。建议用一个**合成教学型人物**跑通：

> “关系套路识别训练员”：使用已经去标识化、拥有处理权的示例对话，生成一个会展示常见不健康沟通模式、并能在用户点击后解释套路的训练角色。

这条切片能同时验证：

- 聊天包导入与说话人映射；
- 模式提炼而非语录复制；
- 证据卡片和冲突处理；
- 有价值的对话与复盘；
- 合成人物标签、隐私脱敏和安全边界；
- 导入、预览、版本、导出全流程。

第二条切片再用“用户蒸馏自己”，第三条才考虑经授权的真实私人个人。

## 17. 开工前需要冻结的产品决策

以下决策会影响数据库和交互，实施前需要产品负责人确认：

1. 第一条纵向切片是否采用“关系套路识别训练员”。
2. 首版是否严格只允许私有人物，不提供分享链接。
3. 首版输入格式是否按 TXT / Markdown / CSV / JSONL / ZIP 冻结。
4. 是否接受“人物包是可移植资产，但不承诺跨任意 AI 产品直接运行”的边界。
5. “个人主页”首版是否仅指登录后的私人主页；仅链接和个人公开主页是否放到 Phase D。
6. 产品界面主名称使用“女娲工坊”，还是直接使用“蒸馏人”。
7. 多人创作内测前，是否接受从 SQLite 迁移到托管 PostgreSQL。

## 18. 推荐实施顺序

```text
评审并冻结本文档
  → 离线登记女娲方法论固定版本与许可证
  → Persona Version 基础迁移
  → 真实创作者账号与对象存储
  → 异步任务骨架
  → 标准聊天包导入

```
